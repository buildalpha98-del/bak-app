# Deep-dive audit — Build Alpha Kids platform

**Date:** 2026-10-26  **Tree:** `feat/portal-full-brand` @ `f77e4a2` (= `main` @ `dc7b1bf` + the portal-brand commit)
**Method:** read-only. CLAUDE.md read in full; nothing it records as fixed is repeated. Six parallel passes (swallowed query errors / lead-only reads / realtime; RLS + migrations; authorisation + server actions + tokens; money + AI; hydration + performance; crons + duplicates + tests), each cross-checking every claim against `supabase/migrations/*.sql`. ## 1. Summary

Build is green, 1,767 unit tests pass, `tsc` is clean, and none of that reflects the state of the product. The platform's serious problems live in three places the unit suite cannot see: **server actions and RPCs that trust "is signed in" as authorisation**, **RLS policies that let a principal edit columns they must not**, and **queries naming columns that do not exist**, whose errors are swallowed into empty data.

The three things to fix first, in order:

1. **Authorisation (today, before anything else).** An unauthenticated caller can set any staff member's password (§2.1), create an admin account (§2.2), and approve, void or email any centre invoice (§2.3). A coach can promote themselves to admin with one PATCH (§2.6), reassign any shift to themselves (§2.8), and set their own pay rate (§2.9). None of these require a bug to exploit — only the public anon key and a session, and for the first three not even that.
2. **Money.** Parents can mint package credits for free three different ways (§2.4, §2.5), package credits are never decremented on booking (§3.1), the lead coach's stored pay rate is NULL on insert and stale after every swap (§3.2), and the weekly payroll cron has never run (§4.1).
3. **The wrong-column class.** Eleven queries name columns that do not exist: child insights have never seen a skill rating, the feedback page breaks on an ambiguous embed, re-engagement never finds a declining centre, the intelligence page's revenue is always $0, the coach pulse counters are always 0, the punctuality badge is unearnable (§4.3–4.13). The CI guards cannot catch this; §7 describes the one test that would.

A fourth, structural: **`npm run lint` has never run.** `next lint` was removed in Next 16 and no `eslint.config.*` exists (§6.1).

Counts, for scale: 845 exported server actions; 2,761 Supabase query chains, 1,905 of which discard `error`; 89 `catch → return empty` sites; 191 files using raw `console.*`; 0 tests on any of the 22 cron routes.

## 2. S1 — Security

### 2.1 ✔ Anyone can set any staff member's password
- `lib/staff/actions.ts:837-852` `adminResetStaffPassword(userId, newPassword?)`
- A `"use server"` export with **no auth check at all**. Calls `admin.auth.admin.updateUserById(userId, { password })` with the service role and **returns the password**. Imported by `components/staff/staff-detail-view.tsx:59` (a `"use client"` module), so its action ID ships in the browser bundle. Middleware passes every POST through (`middleware.ts:106`).
- Scenario: POST that action ID with the admin's profile UUID (readable from `profiles` by any staff, or from any activity-log row) and a chosen password. The admin account is now the attacker's. `sendStaffPasswordResetEmail` (:858) is ungated the same way.
- Confidence: high. Fix: `requireBulkActor(["admin"])` (already defined in the same file) at the top; never return the password; refuse a caller-supplied `newPassword`.

### 2.2 ✔ Anyone can create admin, ops or coach accounts
- `lib/staff/actions.ts:343` `createStaffMember(data)` — no auth; `admin.auth.admin.createUser` then `profiles.insert({ role: data.role, financial_access })`, role is caller-chosen and `admin` is accepted. Caller `components/staff/add-staff-form.tsx` is a client component.
- Same shape: `lib/launch/import-actions.ts:64/160/245` `importCentres` / `importSchools` / `importCoaches` (no auth, create auth users + profiles + compliance docs, `importedBy` caller-supplied; `components/launch/import-manager.tsx` is client).
- Fix: admin-role check from the session in all four; derive `importedBy` from `getUser()`.

### 2.3 ✔ Any signed-in principal can approve, send, void or "pay" any centre invoice; the launch invoice path needs no session at all
- `lib/outbound-invoicing/actions.ts` — `approveInvoice` (:505), `sendInvoice` (:821, emails the centre a PDF), `recordPayment` (:1045), `voidInvoice` (:1155), `submitForApproval` (:430), `rejectInvoice` (:556), `generateOutboundInvoices` (:235). Each does `getUser()` → `if (!user) return` → `createSupabaseAdmin()` writes. The word `role` appears once in the file, in a notification payload.
- `lib/launch/invoice-actions.ts:34/125/257` `createCentreInvoice` / `createSchoolInvoice` / `updateInvoiceStatus` — **no auth**, service-role writes, `createdBy` caller-supplied, `status: "sent"` emails the director. Imported by the client component `components/launch/invoice-manager.tsx`.
- Scenario: a coach, a parent, a childcare director, or the `/demo/school` visitor (§2.11) marks a centre's invoice paid, voids it, or has it emailed.
- Fix: `requireAdmin()` from `lib/invoicing/payroll-actions.ts:29` (financial-access aware) at the top of each.

### 2.4 ✔ A parent can mint package credits without paying
- `lib/bookings/booking-actions.ts:993-1046` `purchasePackage(packageId, paymentId)`; called from `app/(dashboard)/parent/packages/page.tsx:47-52` *after* Square returns.
- The action never checks that `paymentId` exists, belongs to this parent, is a `package_purchase` for this package, is `completed`, or has not been used. `package_balances.payment_id` references `payments(id)` but is not unique.
- Scenario: a parent calls the action with any payment id they have ever seen (a $20 single-session payment, or one old package payment re-used N times) and receives a full `package_balances` row.
- Fix: create the balance server-side inside `/api/payments/create` when `packageId` is set; `UNIQUE(payment_id)` on `package_balances`.

### 2.5 Parents can give themselves free sessions through RLS alone (three routes)
- `035_bookings_payments.sql:162` parent INSERT on `package_balances` (any `remaining_sessions`, `payment_id` nullable); `:128` parent INSERT on `payments` (any `status`, any amount); `:147` parent UPDATE on own `bookings` with no column restriction.
- Routes: (a) INSERT `package_balances {remaining_sessions: 999}` via the REST API, then `createBooking` (`booking-actions.ts:200-245`) checks only ownership/active/remaining and confirms; (b) PATCH `bookings.total_cents = 0` on a pending booking, then `confirmZeroDollarBooking` re-reads the total from the row and confirms; (c) PATCH `bookings.status = 'confirmed'` directly, or insert a `payments` row and call `purchasePackage` (§2.4).
- `/api/payments/create` verifies Square correctly; the database does not require that path.
- Fix: drop the parent INSERT policies on `package_balances` and `payments` and the broad parent UPDATE on `bookings`; perform those writes with the admin client after Square verification; keep cancellation as a narrow trigger-guarded UPDATE (`status → 'cancelled'`, `cancelled_at`, `cancellation_reason` only).

### 2.6 ✔ A coach can promote themselves to admin
- `006_rls_policies.sql:47` `coach_update_own_profile FOR UPDATE USING (auth.uid() = id) WITH CHECK (auth.uid() = id)`. No column restriction, no column-level grant, and no trigger anywhere in the migrations guards `role`, `also_coaches`, `default_pay_rate` or `status` (grep for `OLD.role` / `NEW.role` / `REVOKE UPDATE (` is empty).
- Scenario: `PATCH /rest/v1/profiles?id=eq.<uid> {"role":"admin"}` with the public anon key and the coach's own JWT. `auth_user_role()` now returns `admin` for every policy; pages that re-read role from the DB open `/admin`.
- The app-side twin: `updateStaffMember(id, data)` (`lib/staff/actions.ts:880`) spreads a caller object whose type includes `role` and `financial_access` into `.update()` with no gate — see §2.13.
- Confidence: high (a dashboard-created trigger not in git would change this; confirm with `\d+ profiles`). Fix: BEFORE UPDATE trigger raising when a privileged column changes and `auth_user_role() <> 'admin'`, or `REVOKE UPDATE (role, also_coaches, default_pay_rate, status) ON profiles FROM authenticated`.

### 2.7 ✔ A portal user can move themselves to another school or make themselves principal
- `062_client_users_welcomed.sql:8` `client_users_update_own_welcome FOR UPDATE USING (user_id = auth.uid())` — no `WITH CHECK`, no column restriction. `centre_id`, `role` (`teacher`/`primary`, 088), `is_primary`, `class_ids` are all writable. The app only ever writes `welcomed_at` and `name`.
- Scenario: a teacher PATCHes `centre_id` to another school's id; `auth_client_centre_ids()` (061:24) follows, giving full read of that school's children, ratings, reports and messages. Or `role='primary', class_ids='{}'` to see every class and the report-card release gate (090).
- Fix: trigger freezing `centre_id` / `role` / `is_primary` / `class_ids` for non-staff, or a column-level grant limited to `welcomed_at, name`.

### 2.8 ✔ Any coach can reassign any shift via `set_session_coaches()`
- `074_rpc_function_privileges.sql:68-120`: SECURITY DEFINER; `GRANT EXECUTE … TO authenticated` (:197, re-asserted 102:21); the staff guard at :83 accepts `role IN ('admin','ops','coach')`. Coaches have no write policy on `session_coaches` (048:89 is admin/ops only) — the RPC bypasses it. `lib/sessions/session-coaches.ts:66` calls the RPC through the cookie client.
- Scenario: `rpc/set_session_coaches {p_session_id: <any>, p_coaches: [{user_id: <self>, is_primary: true}]}` removes the rostered crew and the sync trigger (048:41) sets `sessions.coach_id` to the caller; or the caller removes themselves and the shift flips to `needs_replacement`.
- Fix: guard admin/ops only; the one legitimate coach path (accepting a rerostering offer) validates the `rerostering_events` row and calls the RPC with the admin client.

### 2.9 Coaches set their own pay — rates, overrides and hours — with no approval
- `006:63/66` `coach_write_own_pay_rates` / `coach_update_own_pay_rates`; UI `components/pay-rates/coach-pay-rates.tsx:157` → `lib/pay-rates/actions.ts:156 upsertCoachSessionRate`. The 008 trigger resolves `sessions.pay_rate_resolved` from `pay_rates`, which `priceShiftForCoach` and the weekly payroll batch then pay. No status or approval column exists.
- `075:46` `coach_update_own_sessions USING (coach_id = auth.uid() OR auth_is_session_coach(id))` has no column restriction: a coach can PATCH `pay_rate_override`, `actual_duration_minutes`, `status`, `date`, `centre_id` on any shift they are on; the 008 trigger recomputes pay on `pay_rate_override`. The hours-adjustment approval queue (`lib/ops/decision-actions.ts`) exists precisely because minutes need sign-off; the REST API walks around it.
- The app-side twin: `lib/pay-rates/actions.ts:656-690` `approveHoursAdjustment` checks only `if (!user)` then updates `actual_duration_minutes` through the cookie client — so a coach can approve their own adjustment through the action, too (the follow-up `closeTask` fails on `tasks` RLS, but the pay-bearing write has already landed; no transaction).
- `resolve_session_pay_rate(uuid)` is callable by any coach for any session (074:139) — leaks other coaches' resolved rates.
- Confidence: high; whether rate self-service is an accepted product decision is Jayden's call, but it still feeds payroll unapproved. Fix: `REVOKE UPDATE` on the pay/roster columns of `sessions` from `authenticated` and grant only the coach-editable ones; `approved_by` on `pay_rates`; `requireStaff()` in `approveHoursAdjustment`/`rejectHoursAdjustment`; tighten the resolve function.

### 2.10 A coach can rewrite a submitted invoice's amount
- `006:281` `coach_update_own_invoices FOR UPDATE USING (coach_id = auth.uid())` over `coach_invoices` (`line_items_json`, `total_amount`, `gst_amount`, `status`, `payment_batch_id`). The draft-only rule lives only in code (`lib/invoicing/actions.ts:303-320`); payroll (044 `payment_batches`) consumes these rows.
- Fix: trigger limiting coach transitions to `draft → flagged/ready` and freezing amounts once not draft.

### 2.11 `/demo/school` and `/demo/teacher` hand any visitor a real session, which unlocks every "signed-in only" action
- `lib/demo-session.ts:31-104` mints a session on a fixed `client_users` account for anyone hitting the URL (public by design). The containment comment assumes the worst case is browsing fictional students.
- But `getUser()`-only gates treat the demo user as an actor: §2.3, `markAttendance` (`lib/launch/coach-dashboard-actions.ts:308`), `changeLeadStage` (`lib/crm/actions.ts`), `convertLeadToCustomer` (`lib/crm/conversion-actions.ts`), `scheduleDemoSession` / `recordDemoOutcome` (`lib/crm/demo-actions.ts`), `sendDirectMessage` / `editDirectMessage` / `deleteDirectMessage` (`lib/messages/actions.ts`) — all `getUser` → service-role write, no role check.
- Fix: every service-role write checks `profiles.role` or portal ownership, never merely `user != null`; additionally deny the demo account id in those gates.

### 2.12 ✔ The role-hint cookie is unsigned, prefetch requests skip middleware, and nothing below middleware checks role for `/admin` or `/ops`
- `middleware.ts:97-103` returns `NextResponse.next()` for any request carrying `next-router-prefetch` or `purpose: prefetch`; `:106` for any POST. `lib/auth/route-access.ts:81-96` `parseRoleHint` trusts a plain `bak-role=<uid>:<role>:<status>:<fin>:<coaches>` cookie. There is **no `app/(dashboard)/admin/layout.tsx` or `ops/layout.tsx`**; `app/(dashboard)/layout.tsx:9-45` checks only that a `profiles` row exists. `requireFinancialAccess()` (financial section layouts) is the only server-side role gate on a route.
- Scenario: a coach sends `Cookie: bak-role=<myid>:admin:active:1:0` (or just `purpose: prefetch`) and `/admin/*`, `/ops/*` render. RLS bounds most pages, but these use the service role without a role check and render fully: `app/(dashboard)/ops/onboarding/page.tsx:12` (admin client, no `getUser` at all), `admin/assessments/page.tsx:22`, `lib/launch/dashboard-actions.ts` `getDashboardMetrics` / `getAdminStatusPulse` / `getRecentActivity` (revenue, costs, coach lists), `lib/launch/y1-targets-actions.ts`, `lib/equipment/actions.ts getCoachesSimple/getCentresSimple`, `lib/forms/actions.ts getCoachesForFilter/getCentresForFilter`, `lib/terms/actions.ts getCentresForSelect`.
- Side effects: prefetches also skip the revoked-session cookie wipe, so a banned user's sidebar hovers keep rendering live content.
- Fix: add `admin/layout.tsx` and `ops/layout.tsx` that `getUser()` + read `profiles.role` and redirect; HMAC-sign the role hint, or stop trusting it for anything but routing.

## 3. S2 — Wrong money, wrong records

### 3.1 ✔ Package credits are never decremented when a parent books, and never restored on cancel
- `lib/bookings/booking-actions.ts:231-241` (decrement) and `:645-663` (restore). `035_bookings_payments.sql` has parent SELECT + INSERT policies on `package_balances` and **no UPDATE policy**; no later migration adds one.
- The update runs through the parent-role cookie client → RLS filters the row → 0 rows updated, `decrementError` is null, the code continues and inserts a **confirmed** booking. A 5-session pack books unlimited sessions. (Once §2.5 is fixed by adding a narrow UPDATE policy, §3.4 below becomes a credit-printing bug.)
- Fix: do the decrement with a guarded single statement via the admin client (`UPDATE … SET remaining = remaining - n WHERE id = $1 AND remaining >= n RETURNING id`) and fail the booking when no row returns. This also closes the read-then-write race on the last credit.

### 3.2 ✔ `sessions.pay_rate_resolved` is NULL on insert and one coach stale after every reassignment — the lead is paid the wrong rate
- Trigger: `008_pay_rate_resolver.sql:70-81` (re-created verbatim in `074:121-190`). `BEFORE INSERT OR UPDATE OF coach_id, pay_rate_override, centre_id`, and the body calls `resolve_session_pay_rate(NEW.id)`, which `SELECT`s the **table row** by id — not `NEW`.
- (a) INSERT: the row does not exist yet → NULL. (b) `setSessionCoaches` → 048's sync trigger `UPDATE sessions SET coach_id = new_primary` → BEFORE UPDATE fires → the SELECT sees the **old** `coach_id`. Swapping Abz→Rami stores Abz's rate on Rami's shift; the next swap stores Rami's. Nothing fires on `UPDATE OF date` or when `pay_rates` changes.
- Downstream: `lib/pay-rates/coach-shift-pay.ts:50` lead branch does `payRateResolved ?? profile.default_pay_rate ?? 0`, so a NULL means the lead is paid their flat default, skipping the session-type table. Payroll, earnings card and self-invoice all inherit the stored number and agree with each other; the roster's rate sheet (`lib/pay-rates/actions.ts:374`, live `resolvePayRate`) and the cost projection (`lib/roster/cost-actions.ts:184`) show the session-type rate. Ops sees one number, the coach is paid another.
- Confirm: `select count(*) from sessions where coach_id is not null and pay_rate_resolved is null`, and compare a swapped shift's stored rate with its current lead's rate. Fix: compute from `NEW.coach_id / NEW.pay_rate_override / NEW.centre_id / NEW.date` (or have `set_session_coaches` recompute after the sync), add `date` to the `UPDATE OF` list, backfill.

### 3.3 Lead-branch rate unit ignores session type and ordering
- `lib/pay-rates/coach-shift-pay.ts:50-57`: `coachRates.find(r => r.effective_from <= date)` takes the first row PostgREST returns, any `session_type`, no sort — diverging from `resolvePayRate` (`lib/utils/payRates.ts:104-125`: filter by `centreTypeToSessionType`, sort desc). A coach with childcare `$120 per_session` (2025) and school `$45 per_hour` (2026): a 2-hour school shift stores `$45` (trigger picks school) but the unit comes from whichever row arrives first → `per_session` → paid **$45 instead of $90**.
- Confidence: medium (needs a coach with >1 rate row: `select user_id, count(*) from pay_rates group by 1 having count(*) > 1`). Fix: pick the unit from the row `resolvePayRate` would pick, or store `pay_rate_unit_resolved` beside the rate.

### 3.4 `cancelBooking` has no status guard
- `lib/bookings/booking-actions.ts:619-700`. ## 7. Tests — why 1,767 green tests saw none of this

- `tests/setup.ts:14-66`: the default mock answers every chain with `{ data: null, error: null }` and every method returns the same builder. - CI guard blind spots: `no-direct-coach-id-writes` misses a patch object built elsewhere and passed as a variable, `.rpc()`, SQL in `scripts/`; `no-lead-only-coach-session-reads` scans 600 chars after `.from("sessions")` and stops at the first `;`, so a query built across statements escapes it; `no-role-coach-pool-queries` matches only `.eq("role","coach")` — misses `.in("role", [...])`, `.eq("role", var)`, `.or("role.eq.coach,…")`, `.filter(...)`, and SQL policies (061:116); `no-anchor-in-table-row` misses a `<Link>` as the first child of `<TableRow>` (no offenders found today).

- **The one test that would have caught the whole class, and it is feasible:** a vitest under `lib/__tests__/` that (1) parses `supabase/migrations/*.sql` (CREATE TABLE bodies, ALTER … ADD/DROP/RENAME COLUMN, DROP TABLE) into a table → columns map — a prototype did this for all 103 files in under a second and correctly reports `sessions.time` not `scheduled_start`, `session_coaches.user_id` not `coach_id`; (2) walks `lib/`, `app/`, `components/` for `.from("T")` followed by `.select("…")` and `.eq|neq|in|lt|gt|lte|gte|is|not|order("col")`; (3) tokenises the select string (top-level commas, strip `alias:` and `!fk`, recurse into `embed(…)` via the FK target); (4) fails on any column not in the map.
